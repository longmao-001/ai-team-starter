# Week 1：从第一个 bot 到能交付（步骤 4–7）

Day 1 结束时你有一个能答事的 bot，但还不能**交付**。这一周补四件：派工、收口、台账、回滚。
时间不是重点，**顺序**是：没有第 4 步的派工单，第 5 步的收口就没有可核的东西。

## 步骤 4 第一张派工单（40 min）

- [ ] 六件齐：任务 ID / objective / output / tool guidance / boundaries / acceptance
- [ ] 补两件：`due` 与 `blocked_by`（没有依赖写 `none`）
- [ ] 验收串至少一条**能复制执行**（给命令与期望值，不给形容词）

不满足就别往下走：验收里出现「确认无误」「质量高」「内容完整」。
卡住时：先问「拿这张单换个人来做，他能不能判自己做完？」不能，就是缺验收。
字段原文见 [`03-team-operations/02-dispatch-and-acceptance.md`](../03-team-operations/02-dispatch-and-acceptance.md)。

## 步骤 5 第一次收口（40 min）

- [ ] 对每条验收串跑一次，记下命中数
- [ ] 与执行方的回执对账；不一致就两列都写（它报 vs 实测）
- [ ] `MANIFEST.md` 追加第一行：时间 / 交付物 / 依据 / 字节 / sha256
- [ ] `QUEUE.md` 对应行改 DONE，指回产物路径

不满足就别往下走：只凭执行方说「完成了」就收；或产物在但验收数没跑。
卡住时：拿不到实测数，说明验收串选错了——换成能跑出数的判据，别在错误的判据上硬收。

## 步骤 6 台账三行（30 min）

- [ ] `QUEUE.md` 写三行：一件在跑、一件在等、一件已完成
- [ ] 每行都有 `due` 与 `blocked_by`（`none` 也是值）
- [ ] 状态只用五个值：`TODO / RUN / BLOCKED / DONE / DROP`

不满足就别往下走：状态里出现「进行中」「差不多了」这类数不清的词。
卡住时：三行都凑不出来，说明你其实没有并行的事——那就别建台账，先回去做步骤 4。
模板见 [`03-team-operations/04-ledgers.md`](../03-team-operations/04-ledgers.md)。

## 步骤 7 回滚演练（30 min）

- [ ] 挑一个真实在用的文件，备份并记下原 `sha256`
- [ ] 改一处，验收通过
- [ ] 从备份退回，核对 sha 与改前一致
- [ ] 记一行：时间 / 文件 / 耗时 / 有没有卡住（≤5 分钟）

不满足就别往下走：从没演练过，只有一个备份文件夹。
卡住时：退回后 sha 不一致，说明备份其实是改后的版本——这正是必须演练的理由。
纪律原文见 [`03-team-operations/05-backup-rollback.md`](../03-team-operations/05-backup-rollback.md)。

## 周末复盘（30 min）

三个问题，答案写进 `WEEK1-RETRO.md`：

- 这周哪次返工最贵？**根因**是哪条缺失的规则？（不是「谁不小心」）
- 哪条纪律被跳过了一次？为什么能跳过？补哪条能堵住？
- 下周要加的**唯一**一个角色或工具是什么？（只加一个）

## 常见写歪

- 四项全做但都没写死 → 下周全部失效
- 恢复演练跳过，理由是「备份日志显示成功」→ 日志不等于能还原
- 复盘写成流水账，没有「下次补哪条规则」

## ✗ 常见错法

✗ 把 Week 1 当成「把 03 那一章读一遍」。这四步的价值在**你真跑过一次**：一张真的派工单、一次真的对账、一行真的 sha、一次真的退回。读十遍不替代跑一遍。
