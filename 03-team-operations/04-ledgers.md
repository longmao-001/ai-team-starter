# 四个台账载体

> 台账不是写给人看的历史，是**给下一个接手的人（或下一个会话的自己）用的事实源**。
> 判据只有一条：一个不了解这件事的人，只读这些文件，能不能接手。

## QUEUE 模板（可复制）

```markdown
# QUEUE · {{项目名}}

STAGE: 第 3 步 / 共 7 步（依据：T-0301-07 已派、T-0301-08 blocked_by 07）
WIP: 2 / 3        快照: 2026-03-01 22:40+08

| 任务ID | owner | 状态 | objective | 产物 | due | blocked_by | 可并行 |
|---|---|---|---|---|---|---|---|
| T-0301-07 | 写稿bot | RUN | 科普稿 1800-2200 字 | runs/b0301/07.md | 03-01 22:00 | none | 是，与 06 无关 |
| T-0301-08 | 配音bot | BLOCKED | 07 的配音 | runs/b0301/08.wav | 03-02 12:00 | T-0301-07 | 否 |
```

## QUEUE 的字段纪律
- `状态` 只允许五个值：`TODO / RUN / BLOCKED / DONE / DROP`。写「进行中」这种模糊词，事后数不清
- `blocked_by` 必填，没有就写 `none`
- `可并行` 必须带理由。只写「是」等于没写——下次没人知道当时依据什么判断的
- 顶部 `WIP` 与 `快照` 每次更新状态时重算

## 2. MANIFEST.md —— 交付账（追加式）

```markdown
# MANIFEST · {{项目名}}

> 追加式：写错也追加更正行，不删旧行。

| # | 时间 | 交付物 | 依据 | 字节 | sha256 |
|---|---|---|---|---|---|
| R-01 | 03-01 22:35 | runs/b0301/07.md | 用户 03-01 19:00 要求 | 12,884 | D4E1A3F0…（64位全值） |
| R-02 | 03-02 09:10 | 更正 R-01 的字节数（原报 12,884 实测 12,842） | 复核 | 12,842 | 同上未变 |
```

## 为什么只能追加
台账的价值在于「某个时点的事实长这样」。改历史会让所有基于它的推理失效。

**每行必须能回答四问**：谁交的 / 什么时候 / 在哪 / sha 是多少。缺一样就不是台账，是日记。

## 3. PROVENANCE.md —— 产物现值

```markdown
# PROVENANCE · {{项目名}}

快照: 2026-03-02 09:15+08

| 产物 | 现值 sha256 | 生成方式 | 最后改动来源 |
|---|---|---|---|
| runs/b0301/07.md | D4E1…（64位） | 写稿bot · T-0301-07 | R-01 |
| deliver/final.xlsx | 9C02…（64位） | 汇总脚本 build.py | R-07 |
```

**为什么需要它**：MANIFEST 记的是历史，PROVENANCE 记的是现在。两者对不上，说明有未受控变更——盘上文件变了但台账无行。

## 4. DISPATCH/ —— 派工单原件

```
DISPATCH/T-0301-07.md      # 派工单原文，含五要素与验收串
```

**为什么留原件**：收口时要逐条跑验收串。只有群消息里的派工单，翻记录会翻丢，也没法 diff 出「验收项被改过」。

## 三条通用纪律

1. **派工即记账**：派出去的同时写 QUEUE 行。不要「等它开始做了再记」——没记的那条就是将来的僵尸行
2. **当日回写**：状态变化当天改。隔天补记，时间戳全是编的
3. **单一写者**：每个交付件只有一个正文写者，每个台账文件同理。两个会话并行写同一份台账，必丢一次

## 状态断言模板

写「全清 / 无在途 / 已归档」时，照抄这个形状：

```
QUEUE 无 RUN 行（剩余 TODO 2 / DONE 9 / DROP 1）
MANIFEST 到 R-12，末行 sha256:xxxx…（64位）
PROVENANCE 快照 2026-03-02 09:15+08
```

只写「已全部完成」的断言，一律视为未核。

## ✗ 常见错法

✗ 台账靠事后回忆补记。时间戳是编的，僵尸行会一直挂到有人按 mtime 对账才发现。
