# 备份、干跑、回滚

> 三件套。**备份是三件套里唯一不可事后补救的一步**——干跑能补、回滚能补、备份补不了。

## 三件套

| 步 | 动作 | 判据 |
|---|---|---|
| 1 备份 | 留旧版 + 记旧 `sha256:`（全 64 位） | 备份文件存在，且 sha 与原文件一致 |
| 2 干跑 | 只读 / `--dry-run` / 小样本 | 干跑输出与预期一致，或差异已解释 |
| 3 回滚 | 写明 ≤3 步退回方式，并**真跑一遍** | 回滚演练成功，原文件 sha 恢复 |

**没有 `.bak` 就不算走完三件套。**

## 备份命名与位置

```
{{原文件名}}.bak-{{YYYYMMDD}}-{{HHMM}}
```

- 放同目录（方便脚本一次扫出来），不要放「备份」文件夹——三层之外的备份，出事时没人想得起来
- 每次动手前先 `Test-Path` 确认备份落地，再开始改
- 备份不自动清理。攒多了再统一归档，别在改的过程中删

## 三种干跑方式

| 场景 | 干跑方式 |
|---|---|
| 批量改文件 | 先跑 `--dry-run`，或先拿 1 个样本跑完核对 |
| 批量替换 | **先实测命中数**，不符立即停 |
| 结构变更 | 备份 + 副本上跑一遍 |
| 发布/上线 | 先发到预发环境，用同一套验收串验 |

**批量替换的专门纪律**（这是最容易出事的动作）：

1. 显式区分大小写（很多工具默认不区分，替换后会再命中自己刚写入的文本，产生重复前缀）
2. 用**唯一整串**精确替换，不要用宽松正则做整块替换——正则会命中第一个同结构条目，把 A 的内容替换进 B
3. 改前记计数（行/段/条目），改后再测一遍，对不上就回滚
4. 替换后立刻查残留（搜一遍新文本，看有没有出现两次）

## 失败怎么办

**失败即回滚、留档。**

- 回滚到备份 → 记一行「什么时候试了什么、为什么失败」
- **失败记录比成功记录值钱**：成功只说明这条路能走，失败说明这条路不能走，而且往往还解释了为什么
- 半改的文件必须先退回整份再讨论。半成品状态留着，下一步的人会把它当成品

## 回滚演练（第一周做一次）

1. 挑一个不重要但真实在用的文件
2. 备份 → 改一处 → 验收通过
3. 回滚 → 核对 sha 与改前一致
4. 记一行：演练时间、文件、耗时、有没有卡住

**为什么一定要真跑**：回滚步骤看起来永远很简单，直到你真的去跑——备份其实是改后的版本、备份路径写错、权限不够，这些只有跑一次才知道。

## 不可逆动作清单（做前必须批准 + 双备份）

- 移动 / 删除 / 改名用户的文件
- 覆盖现有交付件
- 改门的阈值或判据
- 发布到公开环境
- 任何带「全部」「清空」「重置」字样的批量操作

## ✗ 常见错法

✗ 备份只做不验。恢复时才发现备份是改后的版本，或者路径压根写错了。
