# skill 绑定：管理 bot 该装哪几件

> 一个常见错误：把所有规则都塞进 instructions。结果是角色卡 5000 字，agent 每轮读一遍，关键条款被自己的字数淹没，改一次要动整个 instructions。
> 正确分工：**instructions 放「你是谁、你负责什么」；skill 放「这类活具体怎么做」。**

## 三个必备（缺一件就会出现对应的病）

| 席位（名字自己起） | 管什么 | 不装会怎样 |
|---|---|---|
| 纪律席 | 报数四件套、负结论回显、回执格式、写域与批准门、三件套、门控纪律、不编造 | 报一个没有口径的数、报「0 条」却不写查了哪里，你会反复替它擦屁股 |
| 项目经理席（作业 SOP） | 判型五步、WIP 上限、日巡、周收口、复盘、六红旗 | 台账变成流水账，没有周期动作，进度靠感觉 |
| 验收席（派工与收口） | 派工六件、可执行验收、收口对账、台账 append-only、常见缺口清单 | 派工单写「确认无误」，收口只能信自报；这是最贵的病 |

## 为什么这三件必须分开，不能合成一份
- **触发时机不同**：纪律每轮都用；作业 SOP 按周期用；收口只在交付时用。合起来会让 agent 每轮读一堆用不上的规则
- **修改频率不同**：纪律一年不动；作业 SOP 每役微调；收口条规每踩一次坑加一条
- **责任人不同**：纪律是全员底线（改了要全员知会）；后两个是本岗位工具

## 装法

## 有 skill 机制的平台（如 DSH / Claude Skill 目录）
1. 建三个目录，每个放一份 `SKILL.md`：`skills/纪律席/`、`skills/项目经理席/`、`skills/验收席/`（名字随你）
2. 每份 `SKILL.md` 开头写 `name` 与 `description`（description 要写**何时该加载**，不是写它多好）
3. 在角色卡里点名：「派工与收口时加载验收席；每轮开工加载项目经理席」
4. 版本化：这三份文件进 git，跟模板一起发版

**判据**：把 `03-team-operations/` 的 md 目录直接挂成 skill，内容不用抄两遍——**同一份正文只许存在一处**，其他位置只留指针。规则复制粘贴不是备份，是分岔起点。

## 没有 skill 机制的平台
降级方案：把 `03-team-operations/` 四个文件放在 bot 的工作目录，角色卡里写死「每轮开工先读 `QUEUE.md` 与 `DISCIPLINE.md`」。
代价是 agent 每轮要花一次读取，换来的是规则有唯一真源。

## 三条边界

1. **第三方 skill = 未审代码，不是文档**。目录里有 `package.json` / `requirements.txt` / `scripts/` 的，一律按可执行代码对待：不 install、不跑脚本，只读它的 `SKILL.md` 与 `docs/`
2. **skill 不能给自己授权**。skill 里写「每周自动归档」不等于拿到了移动用户文件的许可——移动/删除/改名仍然要当轮批准
3. **skill 冲突时的优先级**：角色专属技能更细，通用纪律更硬；**冲突以纪律为准**。这条要写进角色卡，否则 agent 会挑对自己方便的那份执行

## 检查清单

- [ ] 三个 skill 的 description 都写了「何时加载」，不是「能力介绍」
- [ ] 角色卡里点名了触发时机，不是只说「你有这些 skill」
- [ ] 规则正文只有一处，其他位置是链接/指针
- [ ] 三个 skill 已进版本库，改了能在 `git log` 里查到
- [ ] 装完做一次演练：让 bot 收一份假交付，看它会不会自己去跑验收串

## ✗ 常见错法

✗ 同一套规则既写进 instructions 又抄进 skill。两份正文必然分岔，改一处漏一处，最后谁也说不清哪份生效。
