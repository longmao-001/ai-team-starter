# 历史改写记录（force-push 台账）

改写已发布历史是允许的，但**必须留一行**，否则以后没人能回答"这两个版本之间到底动了什么"。

格式：`时间 | 范围 | 旧 sha → 新 sha | 为什么 | 影响面`

| 时间 | 范围 | 旧 → 新 | 为什么 | 影响面 |
|---|---|---|---|---|
| 2026-11-11 | `main`，v1.0.0 之后 1 个提交 | `5f79994` → `f1ae7c7`（中间还经过 `bc70f4f`） | 修假门时，`release.md` 与 `sanitize_scan.py` 的注释为解释规则写出了路径形态，被新正则判 BLOCK；该内容在中间提交里，历史层因此报 2 处。选择压成一个提交，让历史里从未出现过那种写法，而不是豁免自己刚写进去的东西 | `v1.0.0` 不受影响，仍是 HEAD 的祖先；无 tag 独占提交；`v1.0.1` 重新打在 `f1ae7c7` 上 |

## 改写之后必须验两件（否则问题不在正文里，正文扫描永远扫不出来）

```bash
# 1) 旧 tag 是否仍是 HEAD 的祖先（不是祖先 = 已发布版本被甩掉了）
git merge-base --is-ancestor <old-tag>^{} HEAD && echo "ancestor OK"

# 2) 有没有只被 tag 可达、main 里没有的提交（这会造出"tag 拉得到、main 里没有"的悬空版本）
git rev-list HEAD > main.txt
git rev-list <tag> | grep -vFxf main.txt   # 空 = 没有悬空
```

外加一条，也是本轮实测出来的**反直觉事实**：**force-push 之后，旧提交在远端仍然取得到**。

用 GitHub API 按旧 sha 查（`GET /repos/{owner}/{repo}/commits/{sha}`），本次改写掉的 `5f79994` 仍然返回 200，内容一字不差。因为改写只移动引用，**不删除对象**；服务端要等自己 GC 才会清，何时清不由你决定。

结论（比前面几条都要紧）：

- 改写历史只解决"引用指向哪里"，**不解决"内容还在不在"**；
- 所以**真实敏感信息不能靠 force-push 处置**，要走仓库删除重建、或平台方的敏感数据流程；
- 本次改写针对的是"我们自己刚写进去的规则示例"，不是敏感信息，因此可接受——但台账里必须写清这个区别，别让后来人以为 force-push 能当脱敏手段用。
