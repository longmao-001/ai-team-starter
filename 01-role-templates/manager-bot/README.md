# 管理 bot 模板（Manager Bot）

> 面向：一个人带一队 AI 员工（3–15 个），自己不可能盯每一轮时，需要的那一个「对执行负责」的 bot。
> 本目录正文由项目经理负责填写；结构沿用仓库占位壳，**五节顺序固定**。

## 要不要建：四个判据

| 你的情况 | 要不要 | 为什么 |
|---|---|---|
| 只有 1–2 个 bot，每轮你都在场 | 不要 | 你就是调度，加一层只多一次转述 |
| 3 个以上 bot，常有两项并行 | 要 | 需要一个「谁在跑、卡在哪」的单一入口 |
| bot 之间会互相派活 | 必须要 | 否则派工单散在各会话，没人对「收齐」负责 |
| 想让它替你做专业判断 | 不要 | 专业判断归专家，它只对「收没收齐」负责 |

## 五节：本目录怎么覆盖

| 节 | 要回答的问题 | 落在哪个文件 |
|---|---|---|
| 1 判型 | 这个任务属于哪一类？该派给谁？ | `02-work-contract.md` 判型 |
| 2 派工 | 派工单里必须写清哪几项？ | `02-work-contract.md` 派工 + 作业台 `02` |
| 3 收口 | 拿什么判「交齐了」？ | `02-work-contract.md` 收口 + 作业台 `02` |
| 4 门控 | 哪些门必须跑现成脚本？不过怎么办？ | `02-work-contract.md` 门控 + 作业台 `03` |
| 5 台账 | 在途表怎么记、谁会腐烂？ | `02-work-contract.md` 台账 + 作业台 `04` |

## 三条硬规矩

1. **派工单必须有任务 ID**，收口时在同一处回复；没有 ID 的派工不算派工。
2. **门控只跑现成脚本**，不改阈值、不放宽；跳过不等于通过。
3. **台账只许生成器写**，多人手改必然覆盖。

## 15 分钟填完的顺序

1. 复制 `01-role-card.md`，把 `{{...}}` 换成你的实际——这份就是 bot 的 instructions
2. 打开 `02-work-contract.md`，**删掉**五条主线里不适用的（删比加重要）
3. 按 `03-skill-bindings.md` 装三个席位 skill
4. 建 `../03-team-operations/` 里的载体，最小可用只要一个 `QUEUE.md`
5. 拿 `04-example-filled.md` 对照填法，用 `05-anti-patterns.md` 自检

## 行业实例去哪找

不在本目录，去 `../05-examples/`。方法章只讲方法：掺了例子的模板，读者会照着例子抄，而不是填自己的坑。

## 文件清单

| 文件 | 给谁 | 什么时候用 |
|---|---|---|
| `01-role-card.md` | 建 bot 的人 | 一次，建 bot 时 |
| `02-work-contract.md` | 管理 bot 自己 | 每轮开工前对照 |
| `03-skill-bindings.md` | 建 bot 的人 | 一次，装 skill 时 |
| `04-example-filled.md` | 不确定怎么填的人 | 只看填法，别照抄 |
| `05-anti-patterns.md` | 所有管理 bot | 角色卡写完自检 |

## 常见写歪

- 管理 bot 自己下场写正文（越权且不可复核）
- 派工单只写「帮我看看 XXX」，没有输入、输出、验收、截止
- 台账靠人回忆更新，一周后全是僵尸行
- 规则全塞进 instructions，关键条款被自己的字数淹没

✗ 常见错法：把这一页当成角色卡。这一页只回答「要不要建、先填哪个」；真正粘进 bot 的是 `01-role-card.md` 填好的那一份。
